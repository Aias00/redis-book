# 第 10 章　复制、延迟与故障后的数据

## 10.1 异步复制的含义

主节点处理写入，并把复制流发送给副本。副本可能落后；从副本读取可获得旧值。写入主节点成功返回，只能证明该次操作在主节点所提供的语义下完成，不能自动证明所有副本都已收到并持久化。

首次同步可能传输完整数据；短暂断连后，若复制积压中仍有需要的历史，可部分同步。积压大小应根据写入速率和预期断连时间规划，不能把默认值当作适合所有环境。

## 10.2 观察复制

```redis
INFO replication
ROLE
```

关注角色、链路状态、复制偏移和副本延迟。在独立副本实例上使用 `REPLICAOF host port` 建立复制前，要确认它的数据可以被主节点数据替换。不要把实验命令运行到已有业务副本上。

主从延迟不只来自网络：副本磁盘压力、慢命令和主节点积压也会参与。读写分离的收益需要和一致性要求一起看；刚修改后的订单状态通常不应无条件从落后副本读取。

## 10.3 WAIT 不是共识协议

`WAIT 1 1000` 等待当前连接此前写入被指定数量的副本确认，返回实际确认的副本数。它减少部分故障下丢失的概率，但不把 Redis 变成强一致的共识数据库，也不自动保证已确认数据落盘。超时返回的数量不足，不表示此前写操作被撤销。

```redis
SET lab:replicated value
WAIT 1 1000
```

单实例实验中没有副本，通常返回 0，键仍然已被写入。Redis 7.2 的 `WAITAOF` 面向 AOF 同步确认，是不同层面的能力；是否能满足业务承诺仍取决于故障模型、选主与存储系统。

## 10.4 限制不等于保证

`min-replicas-to-write` 与 `min-replicas-max-lag` 可在健康副本不足时拒绝部分写入，牺牲可用性来降低风险，但并非每个写入的强一致提交协议。发生网络分区后，旧主和新主之间的结果仍要按实际切换过程分析。

练习：客户端收到主节点写成功后主机立即失联，新主为什么可能没有该值？如果下单后必须立刻看到新状态，描述一种读路由方案及其失败处理。
