# 第 13 章　缓存一致性与失效策略

## 13.1 Cache Aside 的基本流程

读取时先查缓存，未命中再查数据库，并把结果写回缓存。更新时先提交数据库，再删除相应缓存，是常见的 Cache Aside 实践。数据库是事实来源，缓存是可以重建的加速层；应先把这个责任说清楚。

更新数据库后删除缓存仍存在失败窗口：数据库提交成功而缓存删除失败，就会继续读到旧值。可通过事务消息、可靠事件表（outbox）或变更订阅驱动重试，并用 TTL 限制残留时间。TTL 给出的是在特定刷新规则下的陈旧窗口，不能证明强一致。

## 13.2 两个并发请求的反例

初始缓存没有数据。请求 A 从数据库读到旧版本 v1；请求 B 把数据库更新为 v2 并删除缓存；A 随后把 v1 回填到缓存。即使 B 按“先更新再删除”执行，缓存仍可能回到旧值。

延迟双删可以减少部分竞态发生概率，但延迟选择依赖执行时间与网络，无法作为严格正确性证明。需要更强约束时，可按实体串行化变更和回填、使用有序版本及拒绝旧写的协议，或直接让关键读取走数据库。版本保护本身也要处理缓存不存在、淘汰和故障恢复后的版本信息丢失。

## 13.3 空值、热点和雪崩

缓存不存在的业务对象可缓解穿透，但空值必须和“缓存故障”分开表示，并设置较短 TTL。新建对象后要失效空缓存。Bloom Filter 是另一种优化，需要维护更新与误判语义；它不属于本书 7.2 基线的普通基础类型，不能直接假定所有实例都有 `BF.*` 命令。

热点键到期时大量请求同时回源称为击穿，可用进程内请求合并、互斥回填或提前刷新缓解。许多键同时失效、节点故障导致大面积回源，可能形成雪崩；TTL 随机扰动、分级缓存、限流和降级共同控制压力。

TTL 随机化示例：基础 300 秒，加上 0—60 秒均匀扰动。它可以打散整批写入导致的过期峰值，却无法解决 Redis 整体不可用时的回源峰值。

## 13.4 设计验收问题

写清命中率、回源 QPS、最大陈旧时间、缓存不可用时是否放行，以及数据库能否承受降级流量。对错误返回做区分：数据库确实不存在、Redis 超时和反序列化失败，三者不应都被视为业务不存在。

练习：用 A、B 两条时间线重现旧值回填。为一个商品详情接口定义可接受的陈旧时间，再设计数据库提交后失效失败的可重试机制。
