# 第 9 章　RDB、AOF 与恢复演练

## 9.1 先定义损失预算

RPO 表示可接受的数据损失范围，RTO 表示可接受的恢复时间。选择持久化前先回答：能否丢最近一分钟的写入？能否停服十分钟重建？没有这些约束，很难评价某个配置是否“可靠”。

## 9.2 RDB 是时间点快照

RDB 将某个时间点的数据序列化到紧凑文件，适合备份、迁移和快速载入。后台快照通常通过 fork 子进程完成，父进程继续处理请求；fork 停顿、写时复制和磁盘负载仍可能影响线上延迟与内存。

```redis
BGSAVE
INFO persistence
LASTSAVE
```

`BGSAVE` 返回启动成功不代表快照已经完成。需要继续观察 `rdb_bgsave_in_progress` 与 `rdb_last_bgsave_status`。从上次成功快照之后的写入，若没有其他恢复来源，可能丢失。

## 9.3 AOF 是写操作记录

AOF 记录写操作，并通过重写压缩历史。`appendfsync always` 更频繁同步，成本更高；`everysec` 常用于性能与损失窗口的折中；`no` 依赖操作系统刷盘。`everysec` 通常描述约一秒量级的损失风险，不能当成任何磁盘阻塞、系统异常下的严格一秒上界。

Redis 7 采用多文件 AOF：基文件、增量文件和清单协同工作。不要只从目录里随便拷一个文件就声称备份完整。AOF 重写不等于“把所有写入停止后从头再来”，但后台过程仍会占用资源。

```redis
BGREWRITEAOF
INFO persistence
```

实验 Compose 开启 AOF everysec 并保留周期 RDB。两者均开启时，启动通常优先使用 AOF 恢复，因为它可能更完整。实际文件目录与配置必须一起核对。

## 9.4 恢复是备份的验收

一个可执行的恢复流程包括：记录版本与配置；确认快照/重写完成；按官方多文件 AOF 备份规则获得一致的文件集合，或在隔离教学环境停止实例后复制完整数据目录；为备份计算校验和；在新目录和独立端口启动兼容版本；核对数据与 TTL；记录耗时。

`docker compose restart redis` 只验证该卷的正常重启，不能证明离线备份可用，也不能证明断电损失上界。故障演练要区分正常停机、进程崩溃、主机掉电与磁盘损坏。

练习：如果副本实时复制了错误删除，它能作为历史备份吗？为什么 RDB 文件的存在不足以证明可恢复？制定一次包含数据核对和耗时记录的恢复演练。
