# 第 2 章　键、命名空间与生命周期

## 2.1 键设计就是接口设计

键名应表达业务实体、标识和用途，例如 `book:user:42:profile`。环境通常由独立实例或集群隔离；租户信息是否进入键名取决于隔离策略。不要把邮箱、手机号或访问令牌直接拼进键名，因为监控、慢日志和备份都有机会暴露它们。

键越长，重复存储的开销越大；键过短又难以运维。把命名规则写成表格，比让每个调用方自由发挥更可靠。

| 形状 | 类型 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| `book:user:42:profile` | Hash | 随业务失效 | 用户摘要 |
| `book:rank:2026-10` | Sorted Set | 月末归档后过期 | 月排行 |
| `book:request:abc` | String | 按重试窗口保留 | 幂等结果 |

## 2.2 过期是状态的一部分

```redis
SET lab:session token EX 60
TTL lab:session
PTTL lab:session
EXPIRE lab:session 120
PERSIST lab:session
TTL lab:session
```

`TTL` 以秒返回剩余有效期，`PTTL` 使用毫秒；`-1` 表示存在且没有过期时间，`-2` 表示键不存在。普通 `SET` 覆盖键时会移除原 TTL，除非使用 `KEEPTTL`；`INCR`、`HSET` 等原位修改通常保留键的 TTL。

```redis
SET lab:ttl 1 EX 60
INCR lab:ttl
TTL lab:ttl
SET lab:ttl 3
TTL lab:ttl
```

最后返回 `-1`。这类覆盖操作经常造成“缓存为何一直不更新”的问题。需要初次创建和过期一体完成时用 `SET ... EX`，不要在应用中分成 `SET` 和 `EXPIRE` 两个独立步骤。

## 2.3 遍历与删除

`KEYS lab:*` 会一次扫描整个键空间，数据量大时阻塞服务。`SCAN` 用游标渐进遍历，返回数量受 `COUNT` 提示影响，不保证每次恰好多少条，也可能重复返回键。一次完整迭代对始终存在的键有相应遍历保证，但不是一致性快照；并发增删的键是否出现没有完整保证。

```redis
SCAN 0 MATCH lab:* COUNT 100
```

把返回的新游标继续传入，直到游标回到 0；不能因为本批为空就停止。批量处理要幂等，并限制每次删除数量。大对象使用 `UNLINK` 可把主要内存回收工作放到后台，但仍要评估对象结构和异步释放积压。

## 2.4 数据库编号的限制

独立 Redis 可以使用逻辑数据库编号，但它们共享进程资源，并不形成可靠的租户隔离。Redis Cluster 只支持数据库 0。因此应用尽量显式命名和配置，不要依赖“把数据库编号加一”完成水平扩展。
